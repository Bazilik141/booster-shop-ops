# RD-13.1 · Хендоф для Codex — 2 бекенд-залежні задачі

**Проєкт:** Booster Shop (OpenCart, стоковий checkout, який редизайнимо).
**Стан:** презентаційні фікси (8 шт.) вже в патчі `patch-rd13-checkout-qa-fixes-20260710.php`
(лише CSS `boostershop-ds.css` + cache-buster у `checkout.twig`). Цей документ — про
дві задачі, що чіпають payload/валідацію/збереження і потребують рішення на бекенді.

## Ключові файли
- `catalog/view/template/checkout/checkout.twig` — стоковий шаблон + весь inline-JS
  автосейву (`bsCheckoutSyncNpFields`, `triggerRegisterAutosave`, `register.save`,
  `shipping_address|save`, deferred-confirm).
- `catalog/view/javascript/checkout-reskin.js` — лише презентація (переніс полів,

- Референс: `Оформлення замовлення.html` (гість), `Оформлення замовлення - авторизований.html` (авторизований) — збережені рендери реального DOM.

## Задача A — помилка валідації адреси (гість)

### Симптом
Після введення адреси НП та вибору відділення `checkout/register.save` повертає:
```json
{
  "shipping_address_1": "Адреса повинна бути від 3 до 128 символів!",
  "shipping_city": "Назва міста повинна містити від 2 до 128 символів!"
}
```
Тобто на момент валідації обидва класичні поля `shipping_address_1` і `shipping_city`
приходять **порожні**.

### Де це живе
У `checkout.twig` функція `bsCheckoutSyncNpFields()` МАЄ заповнювати ці поля з НП-вводу:
```js
bsSetLastField(registerForm, 'shipping_address_1', address); // address = bsNpAddressText()
bsSetLastField(registerForm, 'shipping_city',      city);    // city = #input-shipping-novaposhta-city
```
де `bsNpAddressText()` повертає рядок відділення (warehouse) або «вулиця, будинок…» для doors.

### Гіпотези для перевірки (в порядку ймовірності)
1. **Гонка/послідовність:** `register.save` серіалізується (`form.serialize()`) РАНІШЕ, ніж
   `bsCheckoutSyncNpFields()` встиг записати значення у приховані поля — особливо на
   шляху `bsCheckoutForceRegisterAutosave` / `focusout.bsSt2a8dForceSave` після вибору
   зі списку `.pinta-dropdown`. Перевірити порядок: sync → serialize → POST.
2. **`bsSetLastField` пише не в те поле:** воно бере `form.find('[name="shipping_address_1"]').last()`.
   У DOM є кілька `shipping_address_1` (класичний in  `#shipping-address` + прихований у
   `#shipping-novaposhta` з `form="form-register"`). Перевірити, що `.last()` — саме той,
   який реально йде в serialize, і що обидва не конфліктують.
3. **Порожній `bsNpAddressText()` для warehouse:** якщо на момент save `#input-shipping-novaposhta-warehouse-address`
   ще не має value (лише `data-ref`), `address` буде `''` → падає валідація 3–128.

### Що дати Codex
- Точні кроки репро + вкладка Network: тіло POST `register.save` (form-data) — видно, чи
  `shipping_address_1`/`shipping_city` реально порожні у payload.
- Лог `console.warn('ST-2a.2 checkout/register.save errors', ...)`.

### Рекомендований напрям фіксу
Клієнтський (без зміни серверної валідації): гарантувати, що `bsCheckoutSyncNpFields()`
відпрацьовує й значення записані ДО серіалізації в усіх трьох шляхах збереження
(`triggerRegisterAutosave`, `bsCheckoutForceRegisterAutosave`, `#form-register submit`).
За потреби — fallback: якщо warehouse ще не має тексту, брати його з обраного пункту
списку. Підтвердити, що після цього повний цикл оформлення проходить (smoke-test).

## Задача B — редагування ПІБ + телефон у «Отримувач» (авторизований)

### Що треба
У розгорнутому блоці «Отримувач» авторизований клієнт має редагувати ПІБ + телефон
(як у гостя). Зараз для авторизованого це **read-only recap**.

### Поточний стан DOM (авторизований)
- Стоковий twig НЕ рендерить картку «Отримувач» (`{% if register or payment_address %}`
  хибне для цього користувача), тож `checkout-reskin.js → ensureReceiverRecap()` будує
  `#bs-co-receiver-recap` — лише текст із обраної збереженої адреси:
  - `[data-co-receiver-line]` = «Ім'я Прізвище · телефон»
  - `[data-co-receiver-address]` = адреса.
- Редагованих полів імені/телефону в DOM авторизованого **немає**.
- Ім'я отримувача, що існує як редаговане — тільки в формі «Додати нову адресу»
  (`#form-shipping-address_nova_poshta`): `shipping_novaposhta_firstname/lastname/middlename`,
  збереження через `POST ?route=checkout/shipping_address|save`.
- **Телефону** як редагованого інпута в авторизованому flow немає (є лише
  `data-bs-customer-phone` на `#checkout-checkout`).

### Чому це не в презентаційному патчі
Немає безпечного save-шляху «як є»:
- Редагування імені **існуючої** збереженої адреси = редагування адреси (address edit),
  а не створення нової. Мірорити в форму «нова адреса» й тригерити її автосейв —
  створить/перемкне адресу. Неправильно.
- Телефон авторизованого = рівень акаунта (`customer.telephone`) або поле замовлення —
  потрібен явний ендпоінт.

### Рішення власника (зафіксовано): B + B — тільки поточне замовлення
- **Телефон:** використати новий телефон **лише для цього замовлення**, акаунт не чіпати.
- **ПІБ:** використати нове ім'я **лише для цього замовлення**, збережену адресу не чіпати.

### Готова фронт-частина
Файл: **`handoff/rd13.1-task-b-receiver-edit.js`** — drop-in заміна `ensureReceiverRecap()`
у `catalog/view/javascript/checkout-reskin.js` + стаб `window.bsCheckoutSaveReceiver`.
Рендерить редаговані поля (Ім'я / Прізвище / По батькові / Телефон), префілить із recap,
живить наявний summary-pipeline (згорнутий рядок оновлюється сам), CSS не потрібен.

### Що лишається Codex (бекенд)
Реалізувати `window.bsCheckoutSaveReceiver({firstname,lastname,middlename,telephone})`:
- Зберігати ці 4 поля як **override на рівні замовлення / сесії checkout** (per-order).
- `checkout/confirm.confirm` має підхопити відредаговані ім'я+телефон у створене замовлення.
- **НЕ** викликати `account/edit` (телефон профілю без змін).
- **НЕ** редагувати обрану збережену адресу (адресна книга без змін).
- Ім'я/телефон не впливають на тарифи доставки → скидати способи доставки не треба.
- Повний контракт (payload, обробка помилок) — у коментарях наприкінці JS-файлу.
