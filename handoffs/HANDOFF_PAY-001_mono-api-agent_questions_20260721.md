# PAY-001 — запит до Mono API-агента

Дата: 2026-07-21  
Статус: потрібна технічна верифікація до будь-якого деплою Phase 2 UI.

## Межа задачі

Потрібен аудит **офіційного API monobank «Покупка частинами»** для наявної OpenCart 4 інтеграції. Не пропонуйте деплой, не просіть і не повторюйте секрети, `store-id`, телефони клієнтів, повні payload-и реальних замовлень або URL адмінки.

Для кожної відповіді дайте посилання на офіційну документацію або sandbox-відповідь з вилученими секретами. Якщо факт не підтверджується — позначте його як `не підтверджено`, а не припускайте.

## Поточний стан, підтверджений із server bundle

- Звичайний checkout наразі використовує SimpleCheckout; майбутній stock `checkout/checkout` готується до cutover.
- `extension/mono_chast/.../model/payment/mono_chast.php` навмисно повертає `[]` з маркером `PAY-001-SIMPLE-CHECKOUT-ISOLATION`.
- Підготовлений, але **ще не залитий** Phase 2 патч додає virtual methods `mono_chast.mono_chast_3|4|5` лише у stock checkout після наявного фільтра Hutko/COD/IBAN.
- Контролер Mono має `confirm()`, `callback()` і `poll()`; його поточний create-запит робить `POST /api/order/create`, очікує HTTP `201` і поле `order_id`.
- Після create контролер зараз повертає браузеру лише `{ success, order_id }`. Він не обробляє URL/deeplink/QR або інший client-action із відповіді API.
- `confirm()` валідує код оплати `^mono_chast\.mono_chast_([345])$`, створює payload з `available_programs: [{ type: "payment_installments", available_parts_count: [parts] }]`, а callback перевіряє Base64 HMAC-SHA256 сирого body з HTTP-заголовка `signature`.
- Значення 500 грн і 3/4/5 зараз є локальними налаштуваннями/обмеженнями; вони не мають вважатися підтвердженими правилами договору, доки це не підтвердить API або договір.

## Критичні питання — блокують деплой

### 1. Старт заявки та дія клієнта

1. Який точний контракт `POST /api/order/create`: обов'язкові поля, типи, допустимі значення, HTTP-коди й обов'язкові response-поля?
2. Що саме повинен зробити браузер після успішного create: відкрити deeplink, редірект, QR, форму/SDK або чекати callback? Яке поле відповіді для цього використовується?
3. Чи достатньо повернути клієнту лише `order_id`? Якщо ні, дайте мінімальний безпечний UX-флоу для web checkout.
4. Чи коректно надсилати один обраний строк як `available_parts_count: [3]` (аналогічно `[4]`, `[5]`), чи API очікує повний перелік доступних строків або інше поле?
5. Чи має список доступних строків отримуватися від API для конкретного кошика/клієнта до створення заявки? Якщо так — назва endpoint і контракт.

### 2. Гроші, товари та склад замовлення

6. У яких одиницях передаються `total_sum` і `products[].sum`: гривні з десятковою частиною, копійки-цілі, ціна одиниці чи сума рядка?
7. Яка інваріанта має виконуватися між `total_sum` та сумою товарів: чи можуть у credit total входити доставка, знижки, подарункові сертифікати, податки й округлення?
8. Чи коректно для рядка `quantity = N` передавати `count = N` та `sum = line_total`, чи `sum` має бути ціною за одну одиницю?
9. Чи обов'язкові `invoice.number`, `invoice.date`, `invoice.source`, `point_id`? Які формати/часова зона/обмеження значень?
10. Які фактичні мінімум, максимум і дозволені `parts` для цього merchant/sandbox; чи вони відрізняються між sandbox і production?

### 3. Авторизація, callback і надійність

11. Підтвердьте алгоритм підпису create: exact raw bytes, HMAC-SHA256, Base64-формат, назви HTTP headers, додаткові timestamp/nonce вимоги.
12. Підтвердьте контракт callback: заголовок підпису, exact body для HMAC, допустимі HTTP-відповіді, retry policy та вимоги до ідемпотентності.
13. Чи існують вимоги до HTTPS, IP allowlist, public callback URL або certificate chain? Чи можлива IP-перевірка callback без ризику зламаних доставок?
14. Чи дозволений polling `/api/order/state`: payload, авторизація, рекомендований інтервал, ліміти та строк, після якого polling треба зупинити?
15. Які ризики повторного create при timeout/мережевій помилці, і яка офіційна ідемпотентна стратегія за `store_order_id`?

### 4. Життєвий цикл і ручне підтвердження магазину

16. Надайте повний перелік `state` / `order_sub_state`, їх переходи й terminal states. Особливо: `WAITING_FOR_CLIENT`, `WAITING_FOR_STORE_CONFIRM`, `ACTIVE`, `DONE`, `RETURNED`, усі `FAIL*`.
17. Які endpoint-и й payload-и потрібні для store confirm, reject і return; коли саме списується перший платіж?
18. Чи може магазин викликати confirm/reject до callback, повторно, або після timeout? Які response/status треба зберігати?
19. Чи є офіційні вимоги до того, коли створювати OpenCart order відносно create-заявки: до create, після create чи після клієнтського підтвердження?
20. Які sandbox-тести й тестові телефони/стани офіційно підтримані зараз? Не наводьте секрети — достатньо опису сценарію та посилання на джерело.

### 5. Сумісність із поточною OpenCart реалізацією

21. Чи сам API вимагає назви payment code, або `mono_chast.mono_chast_3|4|5` — лише внутрішнє мапування магазину? Яке мапування варто зберігати в CRM/NCRM?
22. Чи допустиме створення заявки для вже створеного OpenCart order, а не для «кошика»? Які наслідки, якщо API create успішний, а order/status write у магазині не завершився?
23. Перевірте, чи поточний callback endpoint має використовувати web-safe URL без OpenCart route-separator `|`; якщо для API потрібен інший URL, наведіть точний приклад без домену магазину.
24. Назвіть усі обов'язкові поля, яких бракує у наведеному current payload, і всі поля, які в ньому зайві або семантично неправильні.
