# Codex Report — 3D-P-010 Phase 0: CRM packaging-cost pull

Date: 2026-08-02

## Decision

Do not begin Phase 1. Current-live CRM and 3D-P API evidence is missing, so implementing an automatic cross-system write would be unsafe.

## Confirmed local evidence

The only available main-CRM Apps Script source is the historical patch
`patches/CRM-002_new-order-reservation-fix_20260704.js`, not a current export.
In that source:

- `getPackagingCost_(packagingType, customValue)` resolves standard packaging by exact name in `Розхідники!A4:C`, returning column C; `Інше` uses the supplied custom value.
- `action=orders` groups CRM sales rows but its returned order object contains no `packaging_type` or `packaging_cost`.
- `action=recent_sales` does return `order_id`, `packaging_type`, and aggregate `packaging_cost`, but it was not named as the stable integration contract and is likewise historical only.
- The main CRM `doPost` owns mutations/order sync; no new POST action is proposed.

The dashboard client confirms the named packaging types and custom override exist in `add_sale`/`update_sale` payloads, but it does not contain standard prices.

The local NCRM code separately stores `sales.packaging_cost` and a `packaging_type_id` FK to `consumables`; it is not evidence of the live main Apps Script contract and is not proposed as this task's integration source.

## Missing proof

- No current main-CRM Apps Script export is in the repo.
- No local `BOOSTER_CRM_URL`/`BOOSTER_CRM_TOKEN` or `BOOSTER_3DP_URL`/`BOOSTER_3DP_TOKEN` environment pair is configured, so neither required bounded GET was executed.
- Therefore the current `action=orders` response shape and current live `Продажі` header/order-reference column remain unverified.

## Phase 1 options after evidence

1. If current `orders` exposes order ID, SKUs, packaging type, and resolved cost, use a narrow main-CRM event hook that calls `3dp_write` for the matching 3D-P sale row.
2. If only `recent_sales` exposes the needed fields, explicitly approve it as the stable bounded read contract or add a dedicated read-only order-packaging GET action. Do not infer fields from an old source.

Both options must use `3dp_write` with `expected_current`, retain `_Аудит_API`, perform no main-CRM write from 3D-P, and fail safe on missing standard prices.

## Owner decision needed

Before implementation, provide either a current main-CRM Apps Script export plus the response field names from `action=orders&status=all&limit=1`, or authorize a bounded live read in an environment where the two token pairs are configured. Also provide/confirm the current 3D-P `Продажі` header range through `3dp_get_range`. Redact customer values; field names and the order-reference column are sufficient.

## Addendum — owner-relayed live evidence, 2026-08-02

Owner gave Codex a direct link to the live main-CRM Google Sheet; Codex inspected it live in that separate
session. The finding was relayed to Claude by the owner in chat and is logged here for traceability — it did
not originally land in this file.

**Confirmed live schema:**

- Main CRM `Продажі!P` = resolved packaging cost (money), `Продажі!AC` = packaging type. For multi-line
  orders, the order's total packaging cost is **split across the order's line rows** — e.g. order
  `OC-FOP-0285` has six line rows whose `P` values sum to exactly 5.00 грн. Reading a single row's `P` is not
  the order total; summing `P` across all rows sharing the same `order_id` is required.
- 3D-P sheet already has everything needed on the receiving side: `Продажі!G` (Витрати BoosterShop за од.) is
  the existing write target, `Продажі!N` (№ замовлення) already allows matching a 3D-P row back to a CRM
  `order_id`. **No new column needed on the 3D-P side.**
- `action=orders` still does not return packaging fields (confirmed, matches the original Phase 0 finding
  above). `action=recent_sales` does return aggregated `packaging_cost`/`packaging_type`, but Codex recommends
  against using it for the automatic hook — an event-driven hook already has the exact `order_id` and sum at
  the moment of the event; scanning "recent" sales would be a weaker, racier substitute for no benefit.

**Codex's recommended Phase 1 design** (relayed verbatim by owner, not yet independently re-verified by Claude
against a fresh live read — treat as strong evidence, not yet a closed fact):

1. Hook into the main CRM's existing `apiAddSale_()` and `apiUpdateSale_()` functions; on each call, determine
   whether the order contains a 3D-P SKU.
2. Compute the order's full packaging sum: use an already-computed total if one exists, otherwise sum `P`
   across all `Продажі` rows sharing that `order_id`.
3. Find the matching 3D-P `Продажі` row(s) via `N` (order number).
4. Write the full sum into **exactly one** 3D-P row — the first matching row by row number — never duplicate
   it across multiple 3D-P rows from the same order.
5. Write only through `3dp_write` with `expected_current` (existing optimistic-lock guard).
6. **Fail safe, always**: if no matching 3D-P row exists yet, or the 3D-P API is unreachable, the main-CRM
   order flow must not break — record/log the skip and continue normally. This must never block or fail order
   creation/update.

for the updated Phase 1 scope. The fixture (фурнітура) half of this task is **not** resolved by this evidence
