## 2. Відповіді на п'ять питань §4.2

### 2.1 Чи є обидві адреси в `sitemap.xml`? — **Ні, лише одна**

`sitemap-full.xml` і `sitemap_index.xml` — **побайтово ідентичні файли**
(`sitemap-regen.sh` копіює перший у другий). Станом на 2026-08-21 04:15 у них
13 категорійних URL, серед них:

```
https://boostershop.website/catalog/Pokemon/bustery-pokemon
```

`/catalog/Pokemon-boosters` у карті сайту **немає**. `robots.txt` не забороняє
жодну з двох адрес — він блокує лише фасетні параметри.

### 2.2 Чи посилається щось усередині сайту на `Pokemon-boosters`? — **Ні**

| Де шукав | Результат |
|---|---|
| `ocp5_product_description` (усі 85, `description`/`meta_*`/`name`) | 0 входжень |
| `ocp5_category_description` (усі 15) | 0 входжень |
| `ocp5_information_description` | 0 входжень |
| `ocp5_setting`, `ocp5_banner_image` | 0 входжень |
| 101 twig-шаблон у `catalog/view/template` | 0 входжень |
| `.htaccess` | 0 (три згадки — це `/product/Pokemon-boosters-*`, інші сторінки) |
| `merchant-feed.tsv` | 0 входжень |

Жодна сторінка, банер, меню чи опис не веде на `/catalog/Pokemon-boosters`.

### 2.2.1 Побічна знахідка: меню веде на **третю** адресу

`catalog/view/template/common/header.twig:404` містить жорстко зашитий лінк:

```html
<a href="/catalog/bustery-pokemon" class="bs-menu__sub">Бустери Pokémon</a>
```

Це **не** `Pokemon/bustery-pokemon` і не `Pokemon-boosters`. Адреса все одно
резолвиться, бо `getSeoUrlByKeyword()` шукає
`keyword = ? OR keyword LIKE '%/' . ?` — тобто короткий хвіст шляху теж
підходить. Перевірено живцем 2026-08-22:

```
GET /catalog/bustery-pokemon      -> 200, canonical = /catalog/Pokemon/bustery-pokemon
GET /catalog/Pokemon-booster-box  -> 200, canonical = /catalog/Pokemon/Pokemon-booster-box
```

Тобто в меню — ціла сім'я «коротких» адрес (рядки 403–406, 421–422 у
`header.twig`), і всі вони канонікалізуються правильно. Це поведінка самого
OpenCart, а не дефект даних, і на індексацію не впливає, доки canonical стоїть.
Але це означає: **твердження хендофу «саме на неї (`Pokemon/bustery-pokemon`)
посилається тема» неточне** — тема посилається на `/catalog/bustery-pokemon`.

### 2.3 Чи є `rel=canonical` на обох сторінках і куди він вказує? — **Є, обидва на правильну**

Живі відповіді, 2026-08-22:

| URL | HTTP | `<link rel="canonical">` | `<meta name="robots">` |
|---|---:|---|---|
| `/catalog/Pokemon/bustery-pokemon` | 200 | `https://boostershop.website/catalog/Pokemon/bustery-pokemon` | `index,follow` |
| `/catalog/Pokemon-boosters` | 200 | `https://boostershop.website/catalog/Pokemon/bustery-pokemon` | `index,follow` |
| `/catalog/bustery-pokemon` | 200 | `https://boostershop.website/catalog/Pokemon/bustery-pokemon` | `index,follow` |

Тобто **дубль уже канонікалізований** у правильний бік. `<title>` в усіх трьох
однаковий.

⚠ **Але це збіг обставин, а не гарантія.** Механізм:

```php
// catalog/model/design/seo_url.php
public function getSeoUrlByKeyValue(string $key, string $value): array {
    $query = $this->db->query("SELECT DISTINCT * FROM seo_url
        WHERE key = '…' AND value = '…' AND store_id = … AND language_id = …");
    return $query->row;   // ← перший рядок; ORDER BY немає, LIMIT немає
}
```

`catalog/controller/product/category.php:63` бере `$category_url = $this->url->link('product/category', 'path=' . $path)`,
а рядок 530 віддає його ж у `addLink($category_url, 'canonical')`. Тобто
canonical, усі внутрішні лінки й карта сайту беруться з **одного** запиту без
`ORDER BY`. Зараз InnoDB віддає рядок 1056 (менший PK) — і все сходиться на
`Pokemon/bustery-pokemon`.

Якщо порядок рядків колись зміниться (перебудова таблиці, `OPTIMIZE TABLE`,
відновлення з дампа в іншому порядку, оновлення версії MySQL), **усе
переїде разом**: canonical, меню й карта сайту почнуть вказувати на
`/catalog/Pokemon-boosters`. Карта сайту оновлюється автоматично — cron
`sitemap-regen.sh` о 04:15 щодня (`sitemap-regen.log`, 2026-08-16…21, `OK`), і
вона тягне URL із того самого `url->link` через
`extension/ps_google_sitemap/catalog/controller/feed/ps_google_sitemap.php:227`.

**Це і є справжній ризик.** Не «дві адреси в індексі», а «канонічна адреса
категорії тримається на порядку рядків у таблиці».

### 2.4 Чи є така сама дуплікація в інших категорій? — **Ні, це єдиний випадок**

```sql
SELECT value, COUNT(*) FROM ocp5_seo_url WHERE `key`='path' GROUP BY value HAVING COUNT(*)>1;
-- 59_61 | 2
```

Один рядок у відповіді. Решта 14 категорій мають рівно по одному `path`-рядку.

### 2.5 Коли з'явився рядок `Pokemon-boosters`? — **вікно 2026-06-03 … 2026-06-06, точніше не встановлюється**

| Доказ | Дата | Що показує |
|---|---|---|
| `handoffs/handoff_SEO-CRIT-001_fix-pass.md` (робота по бекапу `backup-6.3.2026`) | 2026-06-03 | категорія 61 жила за адресою `/catalog/Pokemon/Pokemon-boosters` |
| `gsc-indexing-checklist_2026-06-06.md` | 2026-06-06 | у списку вже `/catalog/Pokemon/bustery-pokemon` |
| `plans/sitemap-full.xml` | 2026-06-09 | у карті сайту тільки `bustery-pokemon` |
| `plans/seo-snapshot/2026-06.json` | 2026-06 | те саме |
| `backup-8.5.2026`, `backup-8.16.2026`, `backup-8.21.2026` | 08-05 … 08-21 | обидва рядки, id 1056 і 1068, незмінні |

Тобто слаг категорії міняли на початку червня, і старий рядок пережив зміну.

**Чого встановити не вдалося.** `seo_url_id 1056 < 1068`, тобто
`Pokemon/bustery-pokemon` створений **раніше** за `Pokemon-boosters` — це
суперечить простій версії «стару адресу забули видалити». Правдоподібніше, що
адмінка OpenCart при збереженні категорії видаляє й наново вставляє
`seo_url`-рядки: у діапазоні id 1040–1090 живими лишились тільки 1056, 1068,
1072, 1073, 1074 — решта тридцяти з гаком номерів вигоріла саме так. За такої
механіки `Pokemon-boosters` міг бути вписаний вручну в адмінці вже після
перейменування.

Однозначно відповісти можна лише за бекапом між 2026-06-03 і 2026-08-05.
У репозиторії таких немає; якщо в cPanel лишилися старіші — це закриє питання.
Без них будь-яке твердження про автора рядка буде вигадкою.

## 3. Оцінка ризику під `bs-seo-risk-gate`

| Вимір | Стан |
|---|---|
| Індексований дубль контенту | так, дві 200-адреси з однаковим H1 і 14 товарами |
| Канонікалізація | **вже правильна** на обох адресах |
| У карті сайту | тільки канонічна |
| Внутрішні лінки на зайву адресу | **жодного** |
| Зовнішні лінки на зайву адресу | невідомо — потрібен GSC / Ahrefs |
| Детермінованість | **ні** — залежить від порядку рядків без `ORDER BY` |

Поточний рівень: **низький**. Фактичної шкоди зараз немає.
Рівень при зміні порядку рядків: **високий і мовчазний** — canonical, меню й
карта сайту одночасно переїдуть на адресу, якої немає ні в GSC, ні в жодному
внутрішньому лінку, і це нічого не зламає видимо.

## 4. Два варіанти, підготовані й **не виконані**

Рішення ухвалює власник. Просте видалення рядка без редіректу — **не варіант**:
воно перетворює живу 200-адресу на 404.

### Варіант A — лишити обидва рядки, покластися на canonical

**Що робити:** нічого в БД. Максимум — зафіксувати в
`ROADMAP_SOP`/`context-index`, що адреса `/catalog/Pokemon-boosters` існує
навмисно.

| | |
|---|---|
| Ризик виконання | нульовий |
| Що вирішує | нічого нового; canonical уже стоїть і працює |
| Що лишається | недетермінованість §2.3 — головна проблема **не** знімається |
| Вартість | 0 |

Варіант A у чистому вигляді я не рекомендую: він фіксує стан, у якому
канонічна адреса категорії залежить від порядку рядків у таблиці.

**A+ (дешеве посилення, окрема мікрозадача):** додати `ORDER BY seo_url_id ASC`
у `getSeoUrlByKeyValue()`. Один рядок у
`catalog/model/design/seo_url.php`, ядровий файл OpenCart — правка через
патч-раннер із бекапом. Це прибиває поточну (правильну) поведінку намертво й
знімає весь ризик §2.3, лишаючи дубль жити далі. Зона ризику — SEO, потрібен
Tier 1 смоук.

### Варіант B — 301 з `Pokemon-boosters` на `Pokemon/bustery-pokemon`, і лише потім видалити рядок

**Порядок дій обов'язковий і не переставляється:**

1. додати правило в `.htaccess`:
   `RewriteRule ^catalog/Pokemon-boosters/?$ /catalog/Pokemon/bustery-pokemon [R=301,L]`
   (за зразком `TECH-012_legacy404-301_20260702.php`, який уже додав десять
   таких правил і має перевірений раннер);
2. перевірити живцем: стара адреса віддає рівно один 301, ціль віддає 200;
3. **тільки після цього** видалити `seo_url_id = 1068`;
4. перевірити ще раз: 301 усе ще працює (він тепер із `.htaccess`, не з БД),
   `/catalog/Pokemon/bustery-pokemon` і `/catalog/bustery-pokemon` віддають 200;
5. дочекатися регенерації карти сайту о 04:15 і звірити, що склад URL не змінився.

| | |
|---|---|
| Ризик виконання | середній — `.htaccess` це risky zone (`AGENTS.md`) |
| Що вирішує | знімає дубль **і** недетермінованість разом |
| Пастка | якщо переставити кроки 1 і 3, жива адреса стає 404 |
| Вартість | один патч у `.htaccess` + один DB-патч, два деплої, Tier 1 смоук між ними |

**Моя рекомендація:** B, але не зараз. Спершу закрити WP1 і WP2 — вони вже
готові й стосуються тієї самої категорії 61 (два нові товари стають у неї).
Змішувати вставку товарів із перетасовкою `seo_url` тієї ж категорії в одному
вікні деплою — це самому собі створювати неоднозначність при розборі, якщо щось
піде не так.

Якщо власник хоче мінімальний рух — узяти **A+** зараз (одна правка, знімає
головний ризик), а B лишити на планову SEO-задачу.
