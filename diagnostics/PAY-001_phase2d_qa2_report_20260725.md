## Finding 1 — receiver phone is read from the wrong field

### Evidence

The live Mono drawer builds its phone text in:

```text
catalog/view/template/checkout/payment_method.twig:226
```

using:

```javascript
$('input[name="telephone"]').first().val() || 'вказаний у формі'
```

The visible receiver card is generated by:

```text
catalog/view/javascript/checkout-reskin.js:875-876
```

and its phone input is:

```html
<input type="tel" id="bs-co-recv-telephone" ...>
```

It has no `name="telephone"`, so the Mono selector does not match the field shown to the customer. The receiver value is also mirrored into `data-bs-receiver-telephone` on the checkout root.

### Root cause

Client-side selector mismatch. This is display-only; order creation already applies the saved receiver override in `catalog/controller/checkout/confirm.php`.

### Minimal fix boundary

Change only `catalog/view/template/checkout/payment_method.twig`:

- read `#bs-co-recv-telephone` first;
- keep `#input-telephone` and the checkout root data attribute as compatibility fallbacks;
- update `[data-pay001-phone]` when the receiver phone input changes, not only when the drawer is first rendered;
- do not normalize or mutate the receiver value in this UI patch.

## Finding 2 — the missing delivery tariff is not payment-method-specific

### Regression check

The following current live files are byte-identical to the 2026-07-24 backup:

```text
catalog/controller/checkout/shipping_method.php
  SHA256 9853BA87EF2722B329621D8B517727044EC002E520BA251E18D6C146AA1D203F

catalog/view/template/checkout/shipping_method.twig
  SHA256 5264DD70EF2E9F190207F768C884322CA444018F9595C8DA1FDDE558DABD0845

extension/PintaNovaPoshtaCod/catalog/model/shipping/pinta_nova_poshta.php
  SHA256 75066E88678D6BA3D887BA056E8A027A32C39BD4F2CC8F4EAD23E535657D2B9B
```

The only changes in `checkout-state.js` and `checkout-reskin.js` since that backup are the already-reviewed coupon `summary_html` refresh calls. They do not clear or calculate the shipping tariff.

Therefore selecting Mono, Hutko, COD, or IBAN cannot change the Nova Poshta calculation. All methods show the same blank value because they share the same cart and shipping quote.

### Evidence from the reported QA cart

The screenshot contains 601 units of the QA product `TEST`. The 2026-07-24 product snapshot contains:

```text
weight: 10 g
dimensions: 14 × 7 × 1 cm
shipping: enabled
```

The current Pinta calculator correctly multiplies weight by quantity, but also multiplies every physical axis by quantity:

```php
$products_length = ... $product['length'] ... * $product['quantity'];
$products_width  = ... $product['width']  ... * $product['quantity'];
$products_height = ... $product['height'] ... * $product['quantity'];
```

For 601 units this produces one API seat with approximately:

```text
weight: 6.01 kg
dimensions: 8414 × 4207 × 601 cm
```

Those are not parcel dimensions. When Nova Poshta rejects or cannot price that request and no applicable fixed-rate fallback is returned, `getDocumentPrice()` returns `false`. The chain then behaves as designed:

```text
getBoosterShippingDisplayText(false) -> ''
shipping_display_text -> ''
checkout summary -> '—'
```

### Root cause

Long-standing Pinta package-dimension aggregation defect exposed by the synthetic high-quantity QA cart. It is independent of PAY-001 and independent of the selected payment method.

### Recommended separate fix boundary

Handle this outside the narrow PAY-001 credit UI patch because it affects Nova Poshta pricing for every checkout:

- preserve total-weight multiplication;
- replace per-axis `dimension × quantity` with an explicit, bounded packing rule;
- define a safe result when the API cannot calculate a numeric tariff: an applicable fixed rate or an explicit `За тарифами Нової пошти` state instead of a bare dash;
- keep the ST-2c.5 contract unchanged: delivery remains display-only and must not enter OpenCart payable totals, Hutko amount, Mono amount, or fiscal products;
- optionally add sanitized diagnostic logging for Nova Poshta price failures without API keys or customer data.

The exact packing rule requires owner/Claude approval before implementation because it is a business/shipping decision, not a cosmetic calculation.

## Finding 3 — the preferred credit term is overwritten during UI flattening

### Confirmed working part

The product page correctly appends the selected value:

```javascript
window.location.assign(checkoutUrl + '&mono_chast_parts=' + encodeURIComponent(parts));
```

`catalog/controller/checkout/checkout.php` accepts only 3/4/5 and stores it in:

```php
$this->session->data['pay001_mono_chast_parts']
```

`catalog/controller/checkout/payment_method.php` then returns the same value as:

```php
pay001_preferred
```

### Failure point

In `catalog/view/template/checkout/payment_method.twig`, `flattenPaymentMethods()` sorts the Mono choices but always creates the credit option with:

```javascript
code: monoOptions[0].code
```

`monoOptions[0]` is always the 3-payment option. Although `preferred` correctly contains 4 or 5, the subsequent selection/render path uses `selected.code`, so it:

1. marks 3 payments active;
2. writes `mono_chast.mono_chast_3` into the radio;
3. auto-saves 3 back into the checkout payment state.

### Minimal fix boundary

Change only `catalog/view/template/checkout/payment_method.twig`:

- resolve the preferred Mono option by `group.pay001_preferred`;
- use that option's code as the initial credit `code`;
- preserve numeric 3/4/5 sorting and existing manual term switching;
- keep the server write-boundary validation in `payment_method.php` unchanged.
