## Newly resolved JS dataflow

### Authenticated receiver recap

In current `catalog/view/javascript/checkout-reskin.js`:

- `ensureReceiverRecap()` (843-970) returns if `form-register` exists. It builds a separate authenticated receiver card. The first/middle/last/phone controls are initialized from page receiver attributes and saved-address display fallback.
- `pushEdit` (924-954) reads first/last/middle/phone, writes display attributes and, after basic nonempty first/last/phone checks, calls `bsCheckoutSaveReceiver`. Input events debounce for 400 ms; blur also saves (956-966). Initialization alone does not call the save endpoint, so an authenticated order without a receiver edit can legitimately lack the receiver-patronymic key.
- `bsCheckoutSaveReceiver` (1016-1068) submits a `middlename` property to `checkout/receiver.save` together with an increasing revision. It suppresses repeated payload signatures, aborts an outstanding XHR and ignores stale callbacks. These are source contracts, not proof that every request reaches the server before payment.
- `syncAuthorizedNpRecipient()` (1072-1095) also copies the recap's first/last/middle into the duplicate NP fields; only first/last enter the generic address fields. The recap endpoint is the inspected middle-name persistence path.
- The admitted receiver controller checks authentication, field lengths and revision, then stores order-only session data. Confirm copies an active override into order/header/shipping name snapshots and duplicates `rd13_receiver_middlename` into header/shipping custom fields. It does not edit the customer profile or saved address through this route.

`checkout-state.js` coordinates address/shipping/payment/totals revisions. It neither serializes receiver patronymic nor supplies a receiver-save completion barrier. The receiver-save success handler also does not call that coordinator. No fix to this independent timing concern is proposed here.

## N1 — proposed document-default algorithm

Expected source target: `extension/PintaNovaPoshtaCod/admin/controller/shipping/internet_document.php`. No new JS, shared CSS or metadata. A new Twig target is not required by the current proposal.

1. Retain the full order `shipping_firstname` (with the current outer trim) and the existing `shipping_lastname`. Do not join today's customer or infer a profile identity from the order header.
2. Read `shipping_custom_field` under the actual admin `getOrder()` contract: an array (including a legacy empty array). A missing container can be treated as empty for bounded helper reuse; a null/scalar/object container from corrupt/unsupported data is an invalid snapshot, not an invitation to decode arbitrary shapes or read the profile.
3. Test key existence with `array_key_exists`, not truthiness/`isset`. A string value for `rd13_receiver_middlename` is authoritative, including `''` and `'0'` (do not introduce a truthiness-based fallback). UTF-8/NUL-invalid and non-string values are not cast to a name.
4. With a valid present key, use that middle name and never split the given name. An explicit empty shipping key must win over any header/profile value. There is no fallback to the header's same-named key in this proposal; if the shipping key is absent, that is the owner-decided legacy branch.
5. **Owner decision still required for absent key**, including legacy, guest and authenticated-no-edit orders:
   - **Recommended:** retain full given name, leave patronymic empty for explicit operator entry. This avoids silently classifying the final word as patronymic. A compound given name may still meet the existing NP local-regex refusal; N2 is not implicitly solved.
   - **Alternative:** retain the previous last-word split only for an absent key. This preserves legacy defaults but retains their known ambiguity. Never use this split when the key exists, even when empty or invalid.
6. Invalid containers/values use the full given name and no guessed patronymic, and add a fixed nonpersonal error via the controller's existing GET form error surface: the operator must check and enter the recipient data explicitly. The helper must not mutate the order/customer/address. POST validation uses posted values as before and permits a corrected form submission; do not add a hidden state that permanently prevents correction.
7. Snapshot text is untrusted, including a complete compound given name whose final word was formerly removed. Before rendering the three recipient name controls, apply a context-safe display transformation for their existing double-quoted attributes. Proposed controller-only boundary: for string form data, `htmlspecialchars($value, ENT_QUOTES, 'UTF-8', false)` after valid-UTF-8 admission, preserving already encoded OpenCart request entities without double encoding. Apply only to the three view-bound recipient-name copies after request/API processing, not the saved snapshot or outbound method properties. No raw array/object is rendered. A fixed safe error replaces an invalid default value. Verify GET and POST-error redisplay with quotes, apostrophes, entity text and tag-shaped fixtures. The supplied Twig has autoescape disabled in the admitted loader; this rendering boundary must be tested, not inferred from the template syntax. Sender fields and unrelated controls are outside this boundary.

The selected legacy mode is a reviewed implementation choice, not a live config switch to add silently. The eventual patch should implement the chosen behavior only, with no permanent dual-policy machinery unless the owner separately requires it.
