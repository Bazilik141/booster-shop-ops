## 6. Тіло плану (bs-crm-plan)

### 6.1 What to read (джерела правди)
- **OpenCart-замовлення** — вже читаються через живий hook `addHistory()` → приватна черга → cron-воркер (полагоджено 2026-07-19; cron встановлено 2026-07-26). Джерело типу оплати: поля `payment_method_name` + `payment_method_code` у payload.
- **Supabase `payment_types`** — довідник кодів оплати (read; поповнюється лише міграцією).
- **`app_config`** — комісії по кожному типу (read; MONO вже там з 0013).
- Частота: подієво (на кожне замовлення), не пулінг.

### 6.2 What NOT to touch
- Довідники статусів `order_statuses` / `payment_statuses` — у цьому скоупі не чіпаємо (статус лишається `new`/`unpaid`).
- Round-4 логіка `order_id`/`unit_price` в `index.ts` — підтверджено робоча (#256-#259), не рефакторити.
- `discount_total` баг (`diagnostics/NCRM-10_discount-total-not-mapped_note_20260719.md`) — окрема задача, НЕ згортати сюди.
- MONO типи/комісії в `0013` — робочі, лише доповнюємо ПУМБ окремою міграцією, не редагуємо 0013.
- Ручний облік у майстер-дашборді та його формули — read-only залежність.
- Стандартні protected zones: checkout/payment/фіскалізація UI, sitemap, robots, canonical, Merchant feed, schema.

### 6.3 Що захоплювати в нову CRM (замість «report to build»)
Коректний `payment_type_code` при створенні для всіх живих способів оплати нового чекауту:

| Спосіб оплати (чекаут) | Поточний результат | Має бути |
|---|---|---|
| MONO ПЧ 3/4/5 | `credit_mono_3/4/5` ✅ | без змін |
| ПУМБ ПЧ 3/4/5 | `acquiring` ❌ | `credit_pumb_3/4/5` (новий) |
| Hutko картка | `acquiring` | `acquiring` (лишаємо; = єдиний картковий еквайер) |
| За реквізитами | `bank_details` ✅ | без змін |
| Післяплата / НП | `fop_control` ✅ | без змін |

### 6.4 Derived fields (без запису в джерело)
Комісія рахується у в'юхах через `payment_types.fee_pct_config_key` → `app_config`, як для MONO. ПУМБ-комісії (Додаток №2 договору): `credit_pumb_3`→3.00%, `credit_pumb_4`→4.50%, `credit_pumb_5`→5.80%. Сума надходження = ціна − комісія (банк утримує сам) — обчислюється в репортингу, не пишеться в `sales`.

### 6.5 Coupling with manual workflow
Тип оплати в новій CRM дублює те, що власник зараз бачить у ручному обліку/адмінці OpenCart. Ризик подвійного обліку низький: нова CRM тут — **похідне дзеркало** замовлення, не джерело. Джерело правди для факту оплати лишається ручним (бо статус не синхронізуємо). Це свідоме обмеження скоупу — щоб не створити конфлікт «CRM каже unpaid, а гроші прийшли».

### 6.6 Automation roadmap (фази + гейти)
- **Фаза 1 (зараз, безпечно):** міграція `payment_types` + `app_config` для ПУМБ. Чисті довідкові дані, нічого не ламає. Гейт: review діффа.
- **Фаза 2 (зараз, верифікація відкладена):** гілка ПУМБ у `paymentTypeCode` (index.ts) + редеплой Edge Function. Гейт: smoke на реальному замовленні кожного типу; ПУМБ-гілка вважається неперевіреною до першого реального ПУМБ-замовлення (PAY-002).
- **Фаза 3 (поза цим скоупом, майбутнє):** lifecycle-синхронізація статусів (paid/shipped) — окрема задача, тільки після рішення власника; тягне вебхуки платіжних callback'ів + event-hook на зміну статусу (перетин з PAY-002 §6.5).

## 8. Risks
Зміна `index.ts` — це **живий order-sync для КОЖНОГО замовлення** (той самий шлях, що 2026-07-19 впав мовчки). Помилка в патчі знову зупинить синхронізацію всіх замовлень, не лише ПУМБ. Тому: обов'язковий smoke на реальному замовленні після редеплою (не «локально помилок нема»), і збереження бекапу Edge Function перед деплоєм. Фінансовий ризик: неправильний `payment_type` → неправильна комісія в репортингу; мітигація — перевірити кожен спосіб оплати проти очікуваного коду (§6.3).
