## 6. Тіло плану (bs-crm-plan)

### 6.1 What to read (джерела правди)
- **`currency_rates`** (Supabase, вже є в схемі `0001`) — цільова таблиця запису, `unique(currency, as_of)`, історія по днях, не перезапис.
- **`app_config`** — читає `nbu_rate_buffer_pct` (ще не вставлено жодною міграцією — частина скоупу нижче).
- **Публічні API банків** (без ключів/секретів, це відкриті довідкові ендпоінти):
  - ПриватБанк: `api.privatbank.ua/p24api/pubinfo` (готівковий/безготівковий курс).
  - Monobank: `api.monobank.ua/bank/currency` (ISO 4217 **цифрові** коди валют — потрібен мапінг 840→USD, 978→EUR, 392→JPY, бо `currency_rates.currency` вимагає літерний код `^[A-Z]{3}$`).
  - НБУ: `bank.gov.ua/NBUStatService/v1/statdirectory/exchange` (офіційний курс, без ключа).
  - **MUST-VERIFY:** точну форму відповіді (назви полів buy/sale/rate) Claude з цієї сесії живим викликом не перевіряв — Codex звіряє на реальному виклику перед фіналом, а не вгадує з докстрінгів.
- Частота: раз на добу (cron), не подієво.

### 6.2 What NOT to touch
- Форми закупки (NCRM-09b) — заморозка курсу при вводі закупки (читання `currency_rates` в момент операції) НЕ входить у цей скоуп; зараз `currency_rates` ніде в `lib/`/`app/` не читається, це окрема майбутня задача (вписати курс у форму закупки).
- Order-sync / NCRM-14 (ПУМБ, discount_total) — інший файл, інший скоуп, не чіпати.
- MONO/ПУМБ payment_types, JPY-собівартість mystery-лотів — не входить, лише постачання курсу.
- Protected zones: checkout/payment UI, sitemap/robots/canonical, Merchant feed, schema — не зачіпаються (ця задача суто Supabase-side).

### 6.3 Що будувати (замість «report to build»)
Нова Edge Function (наприклад `currency-rates-fetch`), яка щодня:
1. Для USD, EUR: пробує ПриватБанк, якщо недоступний — Monobank; якщо обидва недоступні — НБУ.
2. Для JPY: завжди НБУ.
3. Коли джерело = НБУ → `rate_to_uah = nbu_rate × (1 + nbu_rate_buffer_pct)` (буфер 1%, з `app_config`). Коли джерело = Приват/Моно → без буфера, курс банку як є.
4. Пише `currency, rate_to_uah, as_of=today, source='ПриватБанк'|'Monobank'|'НБУ'` в `currency_rates`, `on conflict (currency, as_of) do update` (ідемпотентно, повторний запуск того самого дня не дублює рядок).
5. Одна валюта впала (API недоступне/поле не парситься) — не валить весь прогін: лог помилки + пропустити цю валюту на сьогодні, інші валюти пишуться. Ніколи не писати `rate_to_uah <= 0` (є CHECK-constraint, але й на рівні коду теж перевірити).

### 6.4 Derived fields (без запису в джерело)
Немає — ця задача лише постачає `currency_rates`. Використання курсу в собівартості закупки — окрема майбутня задача (не тут).

### 6.5 Coupling with manual workflow
Власник зараз, ймовірно, дивиться курс НБУ вручну при потребі (немає автоматизації). Ризик дублювання низький — нова CRM тут єдине джерело автоматичного курсу; ручного паралельного обліку курсів немає.

### 6.6 Automation roadmap (фази + гейти)
- **Фаза 1 (зараз):** міграція — вставити `nbu_rate_buffer_pct=0.01` в `app_config` (за зразком `0013`/`0014`, ідемпотентно).
- **Фаза 2 (зараз):** Edge Function `currency-rates-fetch` + мапінг Monobank цифра→літера + fallback-ланцюжок §6.3. Гейт: ручний виклик локально/на деплої, перевірити 3 рядки з правильним `source`.
- **Фаза 3 (зараз, нова інфраструктура):** scheduled trigger (pg_cron + pg_net виклик Edge Function, або Supabase Dashboard Cron Jobs — Codex обирає ідіоматичний спосіб для поточної версії Supabase). Це перший scheduled job у проєкті — гейт: дочекатись одного повного циклу (добу) і підтвердити, що спрацював сам, без ручного тригера.
- **Фаза 4 (поза скоупом, майбутнє):** вписати читання `currency_rates` у форму закупки (заморозка курсу при вводі) — окрема задача, після того як Фаза 1-3 стабільні.

## 8. Risks
Нова публічна залежність (3 зовнішні API) — недоступність/зміна формату відповіді банку може мовчки зіпсувати курс або зупинити фетч. Мітигація: try/catch на кожне джерело окремо, лог помилки, ніколи не писати невалідне число, ручна перевірка першого циклу власником. Другий ризик — це перший scheduled job у Supabase-проєкті; неправильно налаштований pg_cron/pg_net може або не спрацювати взагалі (мовчазний фейл, як CHECKOUT-002/NCRM-10 з cron-розкладом), або спрацьовувати частіше/рідше очікуваного. Мітигація: та сама, що для CHECKOUT-002 — не вважати задачу закритою, поки не підтверджено живий цикл без ручного втручання.
